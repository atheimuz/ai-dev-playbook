여러 SubAgent를 동시에 돌리다 보면, 이들이 서로 직접 소통할 수 있으면 더 효과적일 것 같다는 생각이 든다.
Agent Teams가 바로 그 답이다.

## SubAgent의 한계

SubAgent는 별도 컨텍스트에서 작업하고, 결과만 메인에 돌려준다.
메인 컨텍스트가 오염되지 않으니 대규모 탐색 작업에 효과적이다.

하지만 여러 SubAgent를 병렬로 돌리면 3가지 불편한 점이 보인다.

### 1. 팀원 간 소통 불가

SubAgent A가 발견한 내용을 SubAgent B가 알 수 없다.
모든 정보는 메인을 거쳐야 한다.

보안 리뷰어가 "이 API에 인증이 빠져있다"는 걸 발견해도, 성능 리뷰어는 그 사실을 모른 채 같은 API의 최적화만 분석한다.

### 2. 메인이 모든 조율 담당

SubAgent가 5개 돌아가면, 메인은 5개의 결과를 받아서 취합하고, 필요하면 다시 지시하고, 또 결과를 받아야 한다.
메인이 **병목**이 된다.

### 3. 결과 취합 시 컨텍스트 누락

SubAgent는 "요약된 결과"만 돌려준다.
분석 과정에서 발견한 부수적 인사이트나 다른 분석과의 연결 맥락은 사라진다.

### 비유로 정리하면

6명이 같은 방에 있는데, 서로 대화하지 못하고 매니저한테만 보고하는 구조다.

```
SubAgent 구조 (Hub-and-Spoke)

         ┌─── SubAgent A (보안)
         │
         ├─── SubAgent B (성능)
         │
메인 ───┼─── SubAgent C (테스트)
         │
         ├─── SubAgent D (아키텍처)
         │
         └─── SubAgent E (접근성)

* 모든 화살표가 메인을 향함
* SubAgent끼리는 연결 없음
* 메인이 모든 정보의 허브
```

A가 중요한 걸 발견해도, B~E에게 전달하려면 메인을 거쳐야 한다.
메인의 컨텍스트가 커지고, 조율 비용이 늘어난다.

## Agent Teams란?

Agent Teams는 이 구조를 근본적으로 바꾼다.

**핵심 변화 3가지**

- **팀원 간 직접 메시징**: A가 발견한 내용을 B에게 바로 전달
- **공유 작업 목록**: 누가 뭘 하고 있는지 모두가 볼 수 있음
- **자기 조율**: 작업이 끝나면 스스로 다음 작업을 가져감

```
Agent Teams 구조 (Mesh)

리더 ──── 팀원 A (보안)
  │    ╱     │    ╲
  │   ╱      │     ╲
  │  ╱       │      ╲
팀원 B ─── 팀원 C ─── 팀원 D
 (성능)    (테스트)   (아키텍처)

* 팀원끼리 직접 메시지 가능
* 공유 작업 목록으로 현황 파악
* 리더는 조율에 집중
```

### SubAgent vs Agent Teams 비교

| 구분          | SubAgent                    | Agent Teams                    |
| ------------- | --------------------------- | ------------------------------ |
| **컨텍스트**  | 독립 (결과만 호출자에 반환) | 독립 (완전 독립 세션)          |
| **소통**      | 메인에게만 결과 보고        | 팀원끼리 직접 메시지           |
| **조율**      | 메인이 모든 작업 관리       | 공유 작업 목록 + 자기 조율     |
| **최적 용도** | 결과만 필요한 집중 작업     | 논의와 협업이 필요한 복합 작업 |
| **토큰 비용** | 낮음 (요약 반환)            | 높음 (각 팀원이 별도 인스턴스) |

SubAgent가 "보고서를 제출하는 외주"라면, Agent Teams는 "같은 사무실에서 일하는 팀"이다.

## 설정

### 활성화

Agent Teams는 아직 실험적 기능이라 기본적으로 꺼져 있다.
`settings.json`에 환경변수를 추가해서 활성화한다.

```json
{
    "env": {
        "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
    }
}
```

셸 환경변수로도 가능하다.

```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

### 팀 만들기

활성화하고 나서 자연어로 팀 생성을 요청하면, Claude가 팀 구조를 만들고 팀원을 생성하고 작업까지 분배한다.

**코드 리뷰 팀 프롬프트 예시**

```
PR #142를 리뷰할 팀을 만들어줘.
3명의 리뷰어를 생성해
- 보안 관점 리뷰어
- 성능 영향 리뷰어
- 테스트 커버리지 검증 리뷰어
각자 리뷰 후 발견사항을 보고하도록 해.
```

**디버깅 팀 프롬프트 예시**

```
사용자들이 메시지 하나 보내면 앱이 종료된다고 보고하고 있어.
5명의 팀원을 생성해서 서로 다른 가설을 조사하게 해.
팀원끼리 서로의 가설을 반박하면서 과학적 토론처럼 진행해.
합의된 결론을 findings 문서에 정리하도록 해.
```

### 표시 모드

| 모드           | 설명                                     | 장점                  | 설정             |
| -------------- | ---------------------------------------- | --------------------- | ---------------- |
| **In-process** | 메인 터미널 안에서 모두 실행             | 별도 설정 불필요      | 기본값           |
| **Split pane** | 각 팀원이 별도 창에서 실행 (tmux/iTerm2) | 전체 현황 한눈에 파악 | tmux 또는 iTerm2 |

`settings.json`에서 설정할 수 있다.

```json
{
    "teammateMode": "in-process"
}
```

단일 세션에서만 바꾸려면 플래그를 사용한다.

```bash
claude --teammate-mode in-process
```

기본값은 `"auto"`로, tmux 세션 안이면 Split pane, 아니면 In-process로 동작한다.

> Split pane 모드는 tmux 또는 iTerm2의 `it2` CLI가 필요하다.
> VS Code 통합 터미널, Windows Terminal, Ghostty에서는 지원되지 않는다.

### 팀원과 직접 소통

SubAgent와 결정적으로 다른 부분이다.
팀원에게 직접 메시지를 보낼 수 있다.

**In-process 모드**

- `Shift+Up/Down`: 팀원 선택
- `Enter`: 선택한 팀원의 세션 보기
- `Escape`: 팀원의 현재 작업 중단
- `Ctrl+T`: 공유 작업 목록 토글

**Split pane 모드**

- 팀원의 창을 클릭하면 직접 상호작용

**메시지 유형**

- **message**: 특정 팀원 1명에게 전송
- **broadcast**: 모든 팀원에게 동시 전송 (토큰 비용 주의)

## 효과적인 활용 사례

### 잘 맞는 경우

#### 1. 병렬 코드 리뷰

한 명의 리뷰어는 한 번에 한 가지 유형의 이슈에 집중하는 경향이 있다.
관점을 분리하면 모든 영역이 동시에 철저히 검토된다.

```
PR #142를 리뷰할 팀을 만들어줘.
- 보안: 인증, 인가, 입력 검증
- 성능: 쿼리 최적화, 메모리 사용
- 테스트: 커버리지, 엣지 케이스
각자 리뷰 후 발견사항을 보고해.
```

#### 2. 경쟁 가설 디버깅

원인이 불분명한 버그를 여러 가설로 동시에 조사하는 방식이다.
팀원끼리 서로의 가설을 반박하게 만드는 게 핵심이다.

```
로그인 후 세션이 유지되지 않는 버그가 있어.
5명의 팀원이 각각 다른 가설을 조사하게 해
- 쿠키 설정 문제
- 토큰 만료 로직
- 미들웨어 순서
- CORS 설정
- 리다이렉트 처리
서로의 가설을 반박하면서 토론하도록 해.
```

순차적 조사는 첫 번째 가설에 편향되기 쉬운데, 여러 조사관이 서로를 반박하면 살아남은 가설이 실제 원인일 확률이 높아진다.

#### 3. 신규 기능 개발 (계층 분리)

각 팀원이 레이어를 담당하는 구조도 잘 동작한다.

```
사용자 프로필 편집 기능을 만들어줘.
- 팀원 1: React 컴포넌트 (src/components/)
- 팀원 2: E2E 테스트 (tests/)
각자 담당 폴더만 수정하고, 인터페이스가 필요하면 팀원끼리 직접 소통해.
```

#### 4. 동시 조사/리서치

여러 방향을 동시에 탐색하는 것도 유용하다.

```
CLI 도구의 TODO 관리 기능을 설계하려고 해.
팀을 만들어서 여러 관점에서 탐색해
- UX 담당: 사용자 경험과 인터페이스
- 아키텍처 담당: 기술 설계와 확장성
- 비평가: 각 제안의 약점을 지적
```

### 효과가 없는 경우

모든 작업에 Agent Teams가 적합한 건 아니다.

```
Agent Teams 사용 판단

Q1: 팀원들이 병렬로 독립 작업 가능한가?
├── No → 단일 세션 또는 SubAgent
└── Yes → Q2

Q2: 팀원 간 소통/협의가 필요한가?
├── No → SubAgent (결과만 필요)
└── Yes → Q3

Q3: 작업 규모가 조율 비용을 정당화하는가?
├── No → 단일 세션
└── Yes → Agent Teams
```

**오히려 비효율적인 경우**

- **순차적 작업**: A의 결과가 있어야 B를 시작할 수 있는 경우
- **같은 파일 편집**: 두 팀원이 같은 파일을 수정하면 덮어쓰기 발생
- **간단한 작업**: 조율 오버헤드가 작업 자체보다 큼

## 심화 팁

### 계획 승인 모드 (Plan Approval)

복잡하거나 위험한 작업에서는 팀원이 바로 구현에 들어가지 않고, 계획을 먼저 제출하게 만들 수 있다.

```
인증 모듈 리팩토링을 담당할 아키텍트 팀원을 생성해.
변경 전에 반드시 계획 승인을 받도록 해.
```

팀원이 계획을 완성하면 리더에게 승인 요청을 보낸다.
리더가 승인하면 구현을 시작하고, 반려하면 피드백을 반영해 계획을 수정한다.

승인 기준을 리더에게 미리 알려주면 더 효과적이다.

```
테스트 커버리지를 포함한 계획만 승인해.
데이터베이스 스키마를 변경하는 계획은 반려해.
```

### 위임 모드 (Delegate Mode)

기본적으로 리더는 직접 구현 작업도 할 수 있는데, 팀원이 여럿일 때는 리더가 조율에만 집중하는 게 효율적이다.

`Shift+Tab`을 누르면 **위임 모드**로 전환된다.
이 모드에서 리더는 팀원 생성, 메시징, 작업 관리만 할 수 있고 코드를 직접 수정하지 않는다.

### 작업 크기

작업 크기를 어떻게 나누느냐가 결과에 영향을 준다.

- **너무 작으면**: 조율 오버헤드가 작업보다 큼
- **너무 크면**: 팀원이 오래 혼자 작업하다 방향이 틀어질 수 있음
- **적당한 크기**: 명확한 산출물이 있는 자기완결적 단위 (함수 하나, 테스트 파일 하나, 리뷰 보고서 하나)

팀원당 5~6개의 작업을 배분했을 때 가장 잘 돌아간다.

### 토큰 비용

Agent Teams는 각 팀원이 별도 Claude 인스턴스이므로 **토큰 사용량이 크게 늘어난다**.

- **broadcast는 신중하게**: 모든 팀원에게 보내면 비용이 팀원 수만큼 증가
- **병렬 탐색의 가치가 있을 때만**: 리서치, 리뷰, 신규 기능 등
- **루틴 작업은 단일 세션으로 충분**: 간단한 버그 수정이나 파일 편집에 팀은 과함

## 돌아보며

Agent Teams는 "결과만 보고하는 개별 작업자"에서 "서로 소통하며 협업하는 팀"으로의 전환이다.
SubAgent가 전문성의 확장이었다면, Agent Teams는 협업의 확장이다.

팀원들이 서로의 발견을 공유하고, 가설을 반박하고, 스스로 다음 작업을 가져가는 구조는 실제 개발팀의 협업과 비슷하다.
코드 리뷰 팀으로 시작하면 명확한 경계가 있고 코드를 직접 수정하지 않아서 조율 문제가 적다.
거기서 감을 잡고 디버깅이나 기능 개발로 범위를 넓혀가는 접근이 효과적이다.
