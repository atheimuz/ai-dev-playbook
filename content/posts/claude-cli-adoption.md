Claude Chat에서 코드 일부를 복붙하며 "이거 고쳐줘"라고 하는 것과, CLI에서 프로젝트 전체 컨텍스트를 공유하며 "이 기능을 구현해줘"라고 하는 것은 완전히 다른 경험이다.

CLI로 전환하면 AI의 역할이 "조언자"에서 "실행자"로 바뀌고, 개발자는 의사결정에 집중할 수 있게 된다.

## Chat 방식의 한계

Chat에서 Claude를 쓰던 방식은 이랬다.

```
1. 코드 일부 복사
2. Claude Chat에 붙여넣기
3. "이거 리팩토링해줘" / "테스트 코드 만들어줘"
4. 답변 받아서 다시 VSCode에 붙여넣기
5. 컴파일 에러 확인하고 다시 수정 요청
6. 반복...
```

```
문제: Chat 방식의 한계
├─ 복붙 과정에서 컨텍스트 손실 (import 경로, 타입 정의 등)
├─ Claude가 프로젝트 구조를 모르니 부정확한 답변
├─ 내가 설계하고, 구현하고, 테스트 → Claude는 조언자 역할만
└─ 매번 새로운 대화라 이전 결정사항을 다시 설명해야 함
```

결국 **프로젝트의 모든 컨텍스트를 기억하고 전달**하는 건 사람의 몫이었다.

**Chat에서의 대화 예시**

```tsx
// Chat에 물어본 내용
"이 함수 에러 핸들링 추가해줘";

// Claude 답변
try {
    // ... 코드
} catch (error) {
    console.error(error); // 센트리 에러 전송 로직도 넣어줬으면 좋겠는데..
}

// 다시 질문
("이 프로젝트는 reportError 함수를 사용해서 센트리로 에러를 전송해");

// 수정된 답변
reportError(error);
```

프로젝트 컨벤션을 모르니 매번 설명해야 하고, 같은 패턴의 수정을 반복 요청하게 된다.

## CLI 전환 원칙

- **컨텍스트 공유 최대화**: 프로젝트 전체 구조를 AI가 이해하도록 설정
- **위임 범위 확대**: 부분 코드 수정 → 기능 전체 구현으로 확대
- **규칙 기반 일관성**: CLAUDE.md에 프로젝트 규칙 문서화

## 단계별 적용

### 1단계: 프로젝트 컨텍스트 학습시키기

`/init` 명령어로 `CLAUDE.md`를 생성하고, 프로젝트만의 규칙들을 추가한다.

```markdown
## HTML/JSX 작성 규칙

### 버튼 요소

-   `<button>` 태그 사용 시 항상 `title` 속성에 버튼 액션 설명 추가

## 에러 처리

-   `console.log` 사용 금지
-   에러는 반드시 Sentry로 전송

## 파일 구조

-   200줄 넘어가면 파일 분리 고려
-   관련 파일은 같은 폴더에 그룹화

components/
Button/
Button.tsx
Button.test.tsx
Button.styles.ts
index.ts
```

규칙을 정의해두면 매번 설명하지 않아도 Claude가 올바른 방식으로 코드를 작성한다.

### 2단계: 기능 단위 위임

Chat에서는 불가능했던 수준의 위임이 가능하다.

| 구분      | Chat (Before)                     | CLI (After)                                            |
| --------- | --------------------------------- | ------------------------------------------------------ |
| 질문 범위 | "DICOM 파일 업로드 버튼 만들어줘" | "DICOM 파일 업로드 기능을 구현해줘"                    |
| 결과물    | 버튼 컴포넌트 1개                 | 파일 검증, 업로드, 미리보기, 에러 처리, E2E 테스트까지 |

**CLI에서의 위임 예시**

```
"DICOM 파일 업로드 기능을 구현해줘.
요구사항:
- 파일 선택 시 검증 (파일 형식, 크기)
- 업로드 진행률 표시
- 메타데이터 파싱 및 미리보기
- 에러 처리 및 사용자 피드백
- E2E 테스트까지"
```

Claude가 프로젝트 전체를 이해하고 있으니, 기존 함수를 재사용하고, UI 컴포넌트는 디자인 시스템을 적용하고, 에러 핸들링은 프로젝트 규칙대로 처리한다.
한 번의 요청으로 실제 동작하는 기능이 완성된다.

### 3단계: 프로젝트 수준 작업

단순 구현을 넘어서 프로젝트 수준의 작업도 위임할 수 있다.

**코드 품질 개선**

```
"현재 프로젝트에서 테스트 커버리지가 낮은 파일들을 찾아서
우선순위를 정하고, 중요한 것부터 테스트를 추가해줘"
```

**리팩토링 전략 수립**

```
"DICOM 처리 로직이 여러 곳에 흩어져 있어.
구조를 분석하고 개선 방안을 제시한 후,
동의하면 리팩토링까지 진행해줘"
```

### 4단계: 답변 스타일 최적화

`CLAUDE.md`에 답변 가이드를 추가하면 토큰 효율과 가독성이 올라간다.

```markdown
## Claude 답변 가이드

### 간결성 우선

-   불필요한 설명, 사과, 전제 생략
-   핵심만 빠르게 전달
-   코드가 자명하면 설명 생략

### 코드 변경

-   전체 파일 출력보다 수정 부분만
-   같은 패턴의 파일은 첫 번째만 상세히
-   변경 이유는 간단히 (1줄)

### 확인 및 질문

-   애매한 요구사항에만 질문
-   한 번에 하나의 질문만
-   표준 관행은 설명 없이 적용
```

## CLI의 확장 활용

단순히 코드를 작성하는 것을 넘어, 개발 워크플로우 자체를 개선할 수 있다.

**워크플로우 자동화**

```
"현재 브랜치의 변경사항들을 커밋 메시지를 작성하고 PR 템플릿까지 채워줘"
```

**문서 자동 생성**

```
"현재 로그인한 계정의 권한에 따라 어느 페이지에 접속 가능한지,
어떤 기능 권한들이 있는지 문서로 작성해줘"
```

**코드 리뷰**

```
"이번 주 작업한 PR을 리뷰해줘.
특히 성능, 보안, 가독성 측면에서 개선점을 찾아줘"
```

## 트러블슈팅

| 증상                        | 원인                     | 해결책                               |
| --------------------------- | ------------------------ | ------------------------------------ |
| Claude가 프로젝트 규칙 무시 | CLAUDE.md 위치/형식 오류 | 프로젝트 루트에 올바른 형식으로 배치 |
| 이전 대화 컨텍스트 손실     | 새 세션 시작             | /compact로 대화 요약 후 이어가기     |
| 대용량 파일 처리 실패       | 컨텍스트 윈도우 초과     | 관련 부분만 발췌하여 전달            |
| 답변이 너무 장황함          | 기본 답변 스타일         | CLAUDE.md에 간결성 가이드 추가       |
| 코드 스타일 불일치          | 규칙 정의 미흡           | 구체적인 코드 컨벤션 예시 추가       |

## 돌아보며

Chat과 CLI의 가장 큰 차이는 **위임의 단위**다.

| 구분 | Chat                     | CLI                          |
| ---- | ------------------------ | ---------------------------- |
| 역할 | 내가 설계자, AI는 조언자 | AI가 실행자, 나는 의사결정자 |
| 질문 | "이 함수 고쳐줘"         | "이 기능을 구현해줘"         |
| 범위 | 코드 스니펫              | 프로젝트 전체                |

CLI를 쓴다고 자동으로 생산성이 올라가는 건 아니다.
차이를 만드는 건 **AI에게 무엇을 맡길 것인가**다.

1. **명확한 프로젝트 컨텍스트** (`CLAUDE.md`)
2. **작업의 단위를 키우기** (부분 → 전체 기능)
3. **결과가 아닌 목표를 전달** (How → What)
4. **피드백 루프 구축** (점진적 개선)

AI 협업의 핵심은 도구를 사용하는 것이 아니라, **설계와 의사결정에 집중할 수 있도록 실행을 위임하는 것**이다.
