Claude Code에는 커스텀 확장을 위한 세 가지 개념이 존재한다: Agent, Skill, Command.
처음에는 구분이 모호하여 "이 기능을 Skill로 만들어야 하는가, Agent로 만들어야 하는가?"라는 질문이 반복되었다.
그동안의 실사용과 커뮤니티 스킬 분석을 거치며 각 개념의 역할, 선택 기준, 마이그레이션 경로가 정리되었다.

## 핵심 인사이트

세 개념은 각각 다른 추상화 수준에서 동작하며, 분류 기준은 두 축으로 정리된다.

1. **추상화 수준**: 서브실행(Agent) → 단위 도구(Skill) → 워크플로우 오케스트레이션(Command)
2. **트리거 방식**: 자연어 키워드 감지가 필요한가(Skill) vs 명시적 슬래시 호출만으로 충분한가(Command)

| 개념        | 위치                                 | 핵심 속성                                       | 사용 시점                              |
| ----------- | ------------------------------------ | ----------------------------------------------- | -------------------------------------- |
| **Agent**   | `~/.claude/agents/{group}/{name}.md` | 도구 제한 가능, 분석/수정 모두 가능             | 특정 분석이나 수정을 서브태스크로 위임 |
| **Skill**   | `~/.claude/skills/{name}/SKILL.md`   | 독립 호출 가능, 자연어 트리거, YAML frontmatter | 재사용 가능한 단위 기능, 참고문서 주입 |
| **Command** | `~/.claude/commands/{name}.md`       | 순수 마크다운 프롬프트, 명시적 호출             | 다단계 워크플로우 오케스트레이션       |

## 상세

### Agent: 분석용 서브실행기

Agent 도구를 통해 메인 에이전트(사용자와 대화하는 Claude Code)가 생성하는 서브프로세스.
사용자가 `/name`으로 직접 호출할 수 없고, 메인 에이전트가 Agent 도구를 통해 실행한다.
Skill/Command 안에서도, 일반 대화에서도 호출 가능하다.

```
메인 에이전트
  └── Agent(subagent_type="Explore"): "src/ 폴더 구조를 분석하세요"
      → 결과를 텍스트로 반환
```

Agent는 `tools:` 필드로 사용 가능한 도구를 제한할 수 있다.
분석 전용 에이전트는 `Read, Glob, Grep`만 허용하여 읽기 전용으로 운영하고, 수정이나 테스트가 필요한 에이전트는 `Edit`, `Write`, `Bash` 등을 추가로 허용한다.
코드 리뷰의 6개 관점별 분석(아키텍처, 보안, 성능 등)을 각각 읽기 전용 Agent로 병렬 실행하는 것이 대표적인 활용 사례다.

### Skill: 재사용 가능한 도구 + 참고문서

`/skill-name` 또는 자연어로 호출 가능한 독립 단위.
YAML frontmatter로 메타데이터를 정의하고, 마크다운 본문에 워크플로우를 기술한다.
도구(`Bash`, `Read`, `Write` 등)를 직접 사용할 수 있으며, 하나의 집중된 목적을 수행한다.

Skill에는 두 가지 활용 패턴이 있다.

- **실행 도구형**: 트리거 시 특정 작업을 수행한다.
  예: `insight-recorder`(인사이트 기록), `session-analyzer`(세션 분석)
- **참고문서형**: 트리거 시 지식/규칙을 컨텍스트에 주입하여 메인 에이전트의 행동을 가이드한다.
  예: `react-conventions`(컴포넌트 작성 규칙), `react-best-practices`(리렌더링 최적화 패턴)

### Command: 워크플로우 오케스트레이션

여러 Agent와 Skill을 조합하여 복잡한 다단계 워크플로우를 구성한다.
순수 마크다운으로, 자체적으로 도구를 사용하는 것이 아니라 메인 에이전트에게 실행 계획을 전달하는 프롬프트다.

```markdown
# ~/.claude/commands/feature.md

## Phase 1: 기획

product-spec-writer 에이전트로 명세서 작성 → 사용자 확인

## Phase 2: 설계

ux-researcher + ui-designer 에이전트 병렬 실행 → 사용자 확인

## Phase 3: 구현

code-analyst 에이전트로 구현 가이드 생성 → 자동 구현
```

### Skill vs Command: 트리거 방식이 선택 기준

콘텐츠 유형(참조 vs 워크플로우)이 아니라 **사용 패턴**으로 결정한다.

| 기준        | Command                                           | Skill                                       |
| ----------- | ------------------------------------------------- | ------------------------------------------- |
| 트리거 방식 | `/command-name`으로만 실행                        | 자연어 키워드 + `/skill-name` 모두 가능     |
| 파일 구조   | 단일 `.md` 파일                                   | 디렉토리 + `SKILL.md` (멀티 파일 가능)      |
| frontmatter | `allowed-tools`, `description`                    | `name`, `description` (트리거 키워드 포함)  |
| 도구 권한   | `allowed-tools`로 사전 허용 → 실행 시 컨펌 불필요 | 도구 권한 선언 불가 → 매번 사용자 컨펌 필요 |
| 적합한 용도 | 의도적으로 실행하는 워크플로우                    | 자연어로도 자동 감지되길 원하는 기능        |

워크플로우라도 "커밋 나눠줘"처럼 자연어 트리거가 유용하다면 Skill이 맞고, 명시적 실행만 원한다면 Command가 맞다.

**도구 권한의 실질적 차이** — `granular-commit`(커밋 분리) 워크플로우의 경우:

```
Skill로 호출 시:
  git diff 실행 → 🔒 사용자 컨펌
  git stash 실행 → 🔒 사용자 컨펌
  git add 실행 → 🔒 사용자 컨펌
  git commit 실행 → 🔒 사용자 컨펌
  → 반복적인 권한 확인으로 워크플로우가 끊김

Command로 호출 시 (allowed-tools에 git 명령어 사전 등록):
  git diff → ✅ 자동 통과
  git stash → ✅ 자동 통과
  git add → ✅ 자동 통과
  git commit → ✅ 자동 통과
  → 사전 허용된 도구만 사용하므로 매끄럽게 실행
```

도구를 반복적으로 사용하는 워크플로우는 Command의 `allowed-tools`로 사전 허용하는 것이 사용자 경험에서 유리하다.

### 마이그레이션 경로

실사용에서 확인된 진화 패턴:

```
Agent → Skill: "반복되는 지식을 참고문서로 고정하고 싶다"
  예) 테스트 패턴 리뷰 에이전트 → testing-guide 스킬
      Given-When-Then 구조, 모킹 전략 등 동일한 패턴을 반복 제시
      → 분석이 아닌 참조로 전환

Skill → Command: "여러 에이전트를 오케스트레이션해야 한다"
  예) /code-review 스킬 → /code-review 커맨드 (6개 분석 에이전트 조율)

Skill → Command: "명시적 실행만 원한다"
  예) /granular-commit 스킬 → /granular-commit 커맨드
      자연어 매칭이 의도치 않은 트리거를 유발 → 명시적 호출로 전환
```

마이그레이션 판단 기준:

- **Agent → Skill (참고문서)**: Agent가 반복적으로 같은 규칙/패턴을 반환하는가? 실행 결과가 필요한가, 지식 주입만으로 충분한가?
- **Agent → Skill (독립 호출)**: 해당 기능을 `/name`으로 직접 호출하고 싶은가?
- **Skill → Command**: 여러 서브에이전트를 조율하는 고정된 워크플로우인가? 자연어 트리거가 불필요하고 명시적 실행만 원하는가? 또는 반복적인 도구 사용으로 매번 권한 컨펌이 필요한가?

### 커뮤니티에서 워크플로우를 Skill로 만드는 이유

커뮤니티 마켓플레이스에서는 워크플로우 성격이 짙은 기능도 Skill로 배포한다. 세 가지 이유가 있다.

1. **배포 인프라**: 스킬 공유/설치 메커니즘이 `skills/` 디렉토리 기반으로 설계되어 있어, Command를 위한 별도 마켓플레이스가 없다.
2. **키워드 자동 트리거**: Skill은 자연어로도 트리거되므로 사용자가 슬래시 명령어를 몰라도 동작한다. 공유 측면에서 접근성이 더 좋다.
3. **멀티 파일 구조**: Skill은 디렉토리라서 헬퍼 스크립트, 템플릿 등을 함께 번들링할 수 있다.

따라서 로컬에서는 용도에 맞게 Skill과 Command를 분리하되, 공유 목적이라면 배포 인프라와 접근성 때문에 Skill이 현실적인 선택이다.

## 돌아보며

처음에는 Agent, Skill, Command의 경계가 모호해서 비슷한 기능을 다른 형태로 만들어보고, 옮기고, 다시 합치는 시행착오를 반복했다.
결국 "추상화 수준"과 "트리거 방식"이라는 두 축으로 정리되니 판단이 빨라졌다.
Agent가 반복적으로 같은 규칙을 반환하면 Skill 참고문서로 고정하고, Skill이 여러 에이전트를 조율하거나 명시적 실행만 필요하면 Command로 올리는 흐름이 자연스럽게 자리 잡았다.
완벽한 분류를 처음부터 정하려 하기보다, 쓰면서 맞지 않는 부분을 마이그레이션하는 접근이 결과적으로 더 실용적이었다.
