작업하다 반복되는 패턴이 보이면 스킬이나 커맨드로 만든다.
스킬은 자연어 키워드로도 자동 트리거되고, 커맨드는 `/command-name`으로 명시적으로 실행한다.
한번 만들어두면 매번 컨텍스트를 설명할 필요 없이, 한 줄 트리거로 동일한 워크플로우를 재현할 수 있다.
처음부터 계획해서 만든 게 아니라 하나씩 필요할 때 추가해온 것들이다.

## 1. session-analyzer — 사용 점수 자동 채점

세션 로그를 분석해서 Claude Code 사용 품질을 점수로 보여준다.

**동작 방식:**

1. 날짜 범위 질문 (오늘/어제/7일/전체/특정 날짜)
2. JSONL 세션 로그를 Python 스크립트로 분석
3. 사용된 스킬/커맨드/에이전트 동적 수집
4. 4축 스코어링 결과 생성

**4축 스코어링:**

| 축                | 배점 | 측정 내용                     |
| ----------------- | ---- | ----------------------------- |
| 의도 전달력       | 25점 | 한번에 원하는 결과가 나오는지 |
| 작업 효율성       | 30점 | 재수정 없이 처리되는 비율     |
| 도구 적합성       | 25점 | 탐색에 에이전트를 쓰는지      |
| 워크플로우 성숙도 | 20점 | 스킬/커맨드/Plan 활용도       |

스킬/커맨드 목록을 하드코딩하지 않고 동적으로 수집한다.
새 스킬을 추가해도 session-analyzer를 수정할 필요가 없다.

트리거: `/session-analyzer`, "세션 분석", "오늘 뭐했지"

## 2. retrospective — CLAUDE.md 자동 개선

세션에서 발생한 문제를 분석해서 CLAUDE.md, 에이전트, 스킬을 업데이트하는 스킬이다.

**6단계 워크플로우:**

1. 세션 컨텍스트 분석 (같은 파일 3회 이상 수정, 사용자 교정 등)
2. 7개 카테고리 분류 (pattern-mismatch, missing-rule, agent-gap 등)
3. 학습 항목 구조화 (L-001, L-002...)
4. 변경 제안서 작성
5. 사용자 승인 후 적용
6. 결과 확인

회고를 반복하면 CLAUDE.md에 프로젝트 규칙이 점진적으로 축적된다.
규칙이 정교해질수록 에이전트가 같은 실수를 반복하지 않게 되고, 사용자가 매번 교정하는 횟수가 줄어든다.
결과적으로 후속 수정 비용이 크게 감소한다.

**설계 제약:** 서브에이전트를 쓰지 않는다.
대화 컨텍스트 분석이 핵심이라 메인에서 직접 실행해야 한다.

트리거: `/retrospective`, "회고", "CLAUDE.md 업데이트"

## 3. granular-commit — hunk 단위 atomic 커밋 `커맨드`

`git add -p`를 수동으로 하는 대신 변경사항을 논리 단위로 분석해서 커밋을 자동 분리한다.

**두 가지 경로:**

| 경로       | 조건                       | 처리                   |
| ---------- | -------------------------- | ---------------------- |
| fast-path  | 각 파일이 명확히 단일 목적 | 파일 단위로 바로 커밋  |
| patch-path | 한 파일에 여러 목적 혼재   | hunk 분석 후 분리 커밋 |

커밋 메시지는 변경 내용에서 자동 생성한다.
형식은 "feat:", "fix:", "refactor:", "test:" 접두사를 붙인다.

커밋을 상세하게 나누면 좋은 점이 많다.
`git bisect`으로 버그 원인을 빠르게 찾을 수 있고, PR 리뷰어가 변경 의도를 커밋 단위로 파악할 수 있다.
문제가 생겼을 때 해당 커밋만 `revert`하면 되니 롤백 범위가 최소화된다.
커밋 로그 자체가 변경 이력 문서 역할을 하기 때문에 나중에 "왜 이렇게 바꿨지?"를 추적하기도 쉽다.

원래 스킬로 만들었다가 커맨드로 옮겼다.
커밋 분리는 의도적으로 실행하는 워크플로우라 자연어 트리거보다 명시적 `/granular-commit` 호출이 더 자연스럽다.

트리거: `/granular-commit`

## 4. sequence-diagram — 코드 흐름 시각화

특정 함수/기능의 코드 흐름을 분석해서 Mermaid 시퀀스 다이어그램으로 만든다.

**동작 방식:**

1. 진입점(함수명, 파일명, 기능명)을 받아서 코드 탐색
2. 호출 체인 추적
3. Mermaid 다이어그램 생성
4. PNG/SVG로 렌더링

복잡한 호출 체인을 시각적으로 한눈에 파악할 수 있어서 디버깅 시 원인 추적이 빨라진다.
생성된 다이어그램은 코드 리뷰나 신규 멤버 온보딩 시 공유 자료로도 활용할 수 있고, 아키텍처 문서로서의 역할도 한다.

트리거: `/sequence-diagram`, "시퀀스 다이어그램", "코드 흐름 분석"

## 5. bug-fix — 심각도별 파이프라인 분기 `커맨드`

버그를 받으면 심각도를 판단해서 적합한 파이프라인으로 분기한다.

**심각도 분류:**

| 레벨     | 기준                              | 파이프라인                                                                                |
| -------- | --------------------------------- | ----------------------------------------------------------------------------------------- |
| Minor    | UI 오타, 스타일 깨짐 등 기능 무관 | 분석 + 수정 + 검증 루프 (최대 5회)                                                        |
| Major    | 주요 기능 오류, 데이터 표시 문제  | bug-analyzer → 사용자 확인 → bug-fixer + regression-tester + verification 루프 (최대 5회) |
| Critical | 앱 크래시, 데이터 손실, 보안 이슈 | Major와 동일하되 우선순위 최상위                                                          |

**심각도 분류 보충 규칙:**

Minor처럼 보여도 다음 특성이 있으면 Major로 격상한다.

- 첫 시도와 재시도의 동작이 다른 경우 (상태, 캐시, 초기화 순서 등 내부 조건에 따라 결과가 달라짐)
- 수정 방향이 직관적으로 명확하지 않은 경우 (어느 레이어를 고쳐야 하는지 불분명)
- 프레임워크/플랫폼 내부 상태(이벤트 라우팅, 생명주기, 활성화 상태 등)에 의존하는 동작

Major로 격상되면 직감 기반 빠른 수정 대신 bug-analyzer의 정식 분석부터 시작한다.

**핵심 검증 규칙:**

심각도와 관계없이 모든 버그 수정에 적용되는 규칙이다.

- **가정 검증 우선**: 프레임워크/런타임 동작에 의존하는 구현 시, "아마 이렇게 동작할 것" 기반의 구현을 금지한다. 로그 출력이나 테스트 코드로 가정을 먼저 검증한 후 구현한다.
- **2회 실패 시 전환**: 같은 접근법으로 2회 수정해도 해결되지 않으면 즉시 로그/테스트로 실제 동작을 진단하고 접근법을 전환한다. 3회 이상 같은 접근을 반복하지 않는다.
- **자체 검증 루프**: 수정→빌드→자체검증을 한 턴 안에서 성공할 때까지 반복한다. 빌드 성공만으로 끝내지 않고 실제 동작을 확인한다. 사용자에게 "확인해주세요"로 검증을 떠넘기는 것은 자체 검증이 기술적으로 불가능한 경우에만 허용된다.
- **프로젝트 유형별 검증 수단**: 웹앱은 Playwright, 네이티브/데스크톱은 빌드된 바이너리 + 로그 파일, CLI는 직접 실행 + stdout 캡처, 라이브러리는 테스트 코드로 검증한다.

**서브에이전트와 기록 축적:**

Major/Critical은 전담 서브에이전트 4종이 각 단계를 맡는다.
bug-analyzer는 증상과 근본 원인을 분류하고, 수정이 효과 없을 때 선행 조건 체인을 역추적해서 전제 조건부터 확인한다.
bug-fixer는 최소 범위의 코드 수정을, regression-tester는 회귀 테스트 작성을, verification-agent는 테스트 실행과 검증 리포트를 맡는다.

수정 기록은 `.claude/bug-report/{feature}/{bug}/report.md`에 자동 축적된다.
같은 feature의 이전 버그 기록에서 유사 증상, 실패한 접근법, 성공한 수정 패턴을 참고할 수 있어서 같은 실수를 반복하지 않는다.
report.md에는 수정 계획이 todo 체크리스트로 관리되고, 각 시도의 성공/실패 원인이 기록되어 다음 시도의 방향을 잡는 데 도움이 된다.

이것도 granular-commit과 마찬가지로 스킬에서 커맨드로 옮겼다.
버그 수정은 항상 의도적으로 시작하는 작업이라 `/bug-fix`로 명시적으로 실행하도록 했다.

트리거: `/bug-fix`

## 돌아보며

스킬을 너무 많이 만들면 트리거가 헷갈리고 관리가 힘들어진다.
"자주 쓰는 것만" 만드는 게 맞고, 반복되지 않는 작업은 그냥 매번 프롬프트로 요청하는 게 낫다.

스킬과 커맨드 중 뭘 선택할지는 사용 패턴으로 결정한다.
"커밋 나눠줘"처럼 자연어로 트리거되면 좋은 기능은 스킬, `/bug-fix`처럼 항상 의도적으로 실행하는 워크플로우는 커맨드가 맞다.
실제로 granular-commit과 bug-fix를 처음에는 스킬로 만들었다가, 쓰다 보니 자연어 트리거를 쓸 일이 없어서 커맨드로 옮겼다.
