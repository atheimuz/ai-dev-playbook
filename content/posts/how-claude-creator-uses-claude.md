Boris Cherny가 자신의 Claude Code 사용법을 공개했다.
Claude를 만든 사람은 어떻게 Claude를 사용할까?
13가지 팁을 정리하고 실무에 적용할 수 있는 포인트를 뽑아봤다.

## Boris Cherny의 Claude Code 사용법 13가지

### 1. 병렬 실행 환경 구성

터미널에서 5개의 Claude를 병렬로 실행한다.
각 탭에 1~5 번호를 붙이고, 시스템 알림으로 입력이 필요한 시점을 파악한다.

```
병렬 실행의 장점
├─ 대기 시간 최소화: 한 세션이 작업 중일 때 다른 세션 활용
├─ 컨텍스트 분리: 작업별로 독립된 세션 유지
└─ 효율적 멀티태스킹: 여러 작업을 동시에 진행
```

### 2. 웹과 로컬의 병렬 운영

claude.ai/code 웹에서 5~10개의 Claude를 추가로 병렬 실행하고, 로컬 Claude와 함께 운영한다.

| 기능             | 설명                                  |
| ---------------- | ------------------------------------- |
| 핸드오프         | 로컬 세션을 웹으로 전환하여 계속 사용 |
| Chrome 직접 시작 | 브라우저에서 바로 세션 시작           |
| `--teleport`     | 로컬 ↔ 웹 양방향 전환                 |
| iOS 앱 활용      | 아침에 세션 시작, 나중에 결과 확인    |

모바일에서 세션을 시작하고 나중에 확인하는 비동기 작업 방식도 효과적이다.
한 세션에서 코드 작업을 진행하는 동안 다른 세션에서 테스트 코드를 작성하게 하면, 대기 시간 없이 계속 작업을 진행할 수 있다.

### 3. 모델 선택: Opus 4.5 with thinking

모든 작업에 **Opus 4.5 with thinking**을 사용한다.

> **Boris Cherny의 평가**
>
> "지금까지 사용한 최고의 코딩 모델.
>
> Sonnet보다 크고 느리지만, 조정(steering)이 적게 필요하고 도구 활용 능력이 뛰어남.
>
> 결과적으로 작은 모델보다 거의 항상 더 빠른 최종 결과 도출."

작은 모델로 여러 번 수정하는 것보다, 큰 모델로 한 번에 정확한 결과를 얻는 것이 더 효율적이다.

### 4. CLAUDE.md를 통한 팀 단위 지식 축적

Claude Code 저장소에 팀 전체가 공유하는 단일 `CLAUDE.md` 파일을 유지한다.

```
CLAUDE.md 운영 방식
├─ git에 체크인하여 버전 관리
├─ 팀 전체가 주 단위로 여러 번 기여
├─ Claude가 잘못된 행동을 할 때마다 추가
└─ 각 팀이 최신 상태 유지 책임
```

**핵심 포인트**: Claude가 실수할 때마다 `CLAUDE.md`에 기록하면, 같은 실수를 방지할 수 있다.
팀의 암묵적 지식이 명시적 문서로 축적된다.

`CLAUDE.md`에 "이 프로젝트에서는 항상 TypeScript strict 모드를 사용한다", "API 응답 타입은 types/api.ts에 정의한다" 같은 규칙을 기록해두면, 매번 같은 설명을 반복하지 않아도 된다.

### 5. 코드 리뷰 시 CLAUDE.md 업데이트

![코드 리뷰 시 CLAUDE.md 업데이트](/images/posts/how-claude-creator-uses-claude/code-review.png)

코드 리뷰 시 동료 PR에 `@.claude`를 태그해서 PR의 일부로 `CLAUDE.md`에 내용을 추가한다.

- Claude Code GitHub Action(`/install-github-action`) 활용
- Dan Shipper의 [Compounding Engineering](https://every.to/chain-of-thought/compound-engineering-how-every-codes-with-agents) 개념과 유사
- 리뷰 과정에서 발견한 패턴이 자동으로 팀 지식으로 축적

### 6. Plan 모드와 자동 수락 워크플로우

대부분의 세션을 **Plan 모드**(shift+tab 두 번)로 시작한다.

```
Plan 모드 워크플로우
├─ 1. Plan 모드로 세션 시작
├─ 2. Claude와 계획이 만족스러워질 때까지 반복 협의
├─ 3. 계획 확정 후 auto-accept edits 모드로 전환
└─ 4. Claude가 보통 한 번에(1-shot) 완성
```

> **핵심 인사이트**
>
> "좋은 계획이 정말 중요함."

PR 작성이 목표일 때, Plan 모드에서 충분히 협의한 후 실행하면 수정 횟수가 크게 줄어든다.

### 7. 슬래시 커맨드를 통한 반복 작업 자동화

하루에 여러 번 수행하는 "inner loop" 워크플로우마다 슬래시 커맨드를 사용한다.

| 항목      | 설명                                |
| --------- | ----------------------------------- |
| 저장 위치 | `.claude/commands/` 디렉토리        |
| 버전 관리 | git에 체크인                        |
| 예시      | `/commit-push-pr` 매일 수십 번 사용 |

**인라인 bash 활용**: `git status` 등 정보를 미리 계산해서 커맨드에 포함하면, 빠른 실행과 모델과의 불필요한 왕복을 방지할 수 있다.

### 8. 서브에이전트 활용

여러 서브에이전트를 정기적으로 사용한다.

```
자주 사용하는 서브에이전트
├─ code-simplifier: Claude 작업 완료 후 코드 단순화
└─ verify-app: Claude Code 엔드투엔드 테스트를 위한 상세 지침 포함
```

슬래시 커맨드와 마찬가지로, 대부분의 PR에서 수행하는 가장 일반적인 워크플로우를 자동화하는 개념이다.

### 9. PostToolUse 훅을 통한 코드 포매팅

PostToolUse 훅을 사용해 Claude의 코드 포매팅을 자동 처리한다.

- Claude는 기본적으로 잘 포매팅된 코드를 생성
- 훅이 나머지 10%를 처리
- 나중에 CI에서 포매팅 오류 방지

### 10. 권한 관리 방식

`--dangerously-skip-permissions`는 사용하지 않는다.

```
권한 관리 전략
├─ /permissions로 안전한 bash 명령 사전 허용
├─ 불필요한 권한 프롬프트 회피
└─ .claude/settings.json에 체크인하여 팀과 공유
```

보안을 유지하면서도 워크플로우 효율성을 확보하는 방식이다.

### 11. Claude Code의 도구 통합 활용

Claude Code가 모든 도구를 대신 사용하도록 설정한다.

| 도구     | 활용 방식               |
| -------- | ----------------------- |
| Slack    | MCP 서버로 검색 및 게시 |
| BigQuery | bq CLI로 분석 질문 답변 |
| Sentry   | 에러 로그 가져오기      |

Slack MCP 설정은 `.mcp.json`에 체크인하여 팀과 공유한다.

### 12. 장시간 작업 처리 방식

매우 긴 작업의 경우 세 가지 방법 중 선택한다.

```
장시간 작업 처리 옵션
├─ (a) 완료 시 백그라운드 에이전트로 작업 검증하도록 프롬프트
├─ (b) 에이전트 Stop 훅으로 더 결정론적으로 검증
└─ (c) Geoffrey Huntley의 ralph-wiggum 플러그인 사용
```

샌드박스 환경에서는 `--permission-mode=dontAsk`를 사용해 권한 프롬프트 없이 Claude가 작업에 집중하도록 설정한다.

### 13. 가장 중요한 팁: 검증 피드백 루프 제공

> **Boris Cherny가 강조한 가장 중요한 요소**
>
> "Claude에게 작업을 검증할 방법을 제공하면, 최종 결과물 품질이 2~3배 향상된다."

Claude가 claude.ai/code에 랜딩하는 모든 변경 사항을 **Claude Chrome 확장 프로그램**으로 테스트한다.
브라우저를 열고 UI를 테스트하며, 코드가 작동하고 UX가 좋을 때까지 반복한다.

```
검증 방식 예시 (도메인별)
├─ 단순한 경우: bash 명령 실행
├─ 백엔드: 테스트 스위트 실행
├─ 프론트엔드: 브라우저에서 앱 테스트
└─ 모바일: 폰 시뮬레이터에서 앱 테스트
```

**핵심 포인트**: 이 검증 과정을 견고하게 구축하는 데 투자가 필요하다.
피드백 루프가 있으면 Claude는 스스로 수정하고 개선할 수 있다.

## 돌아보며

13가지 중 가장 인상적인 건 **검증 피드백 루프**다.
Claude에게 검증할 방법을 제공하면 결과물 품질이 2~3배 향상된다는 점은, 단순히 프롬프트를 잘 쓰는 것보다 검증 인프라를 구축하는 게 더 중요하다는 뜻이다.

| 우선순위 | 적용 항목                          | 효과             |
| -------- | ---------------------------------- | ---------------- |
| 높음     | 검증 피드백 루프 구축              | 품질 2~3배 향상  |
| 높음     | Plan 모드 → auto-accept 워크플로우 | 수정 횟수 감소   |
| 중간     | CLAUDE.md 팀 공유                  | 반복 실수 방지   |
| 중간     | 슬래시 커맨드 자동화               | 반복 작업 효율화 |

`CLAUDE.md`로 지식을 축적하고, Plan 모드로 충분히 협의하고, 검증 피드백 루프로 품질을 보장하는 구조가 핵심이다.
명확한 계획, 충분한 맥락, 그리고 결과를 확인할 수 있는 방법을 제공하면 최고의 결과를 얻을 수 있다.
